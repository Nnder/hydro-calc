# Доработка обработки персональных данных — 21.10.2026

Обновление опубликовано 22.10.2026. Технические проверки и оставшиеся организационные задачи перечислены ниже; результаты развёртывания — в конце документа. Не копировать старый nuxt.config.ts при следующем развёртывании: он вернёт встроенный SMTP-секрет и автоматическую Метрику.

## До публикации

1. Реквизиты OPERATOR заполнены 22.10.2026 по данным владельца: наименование, ИНН, КПП и юридический адрес. Блокировка по отсутствию реквизитов снята; сервер по-прежнему требует настройки SMTP, получателя и закрытого хранилища. Проверить документы с ответственным за ПД; удалить черновые инструкции, подтвердить список обработчиков и обновить версию. robots noindex можно снять после согласования.
2. Установить NUXT_SMTP_USER и NUXT_SMTP_PASS через закрытый systemd EnvironmentFile, права 0600. Пароль, ранее попавший в исходники/историю и сборки, необходимо сменить в почтовом сервисе. Удаление из текущего кода не отзывает старый пароль. Не публиковать его в коммитах, логах или ответах API.
3. Получить рабочий адрес для NUXT_SPARE_PARTS_MAIL_TO вместо Gmail. Прежние адреса остальных отделов сохранены, неизвестные типы больше не пересылаются на запасной личный ящик. Почта обращений по ПД не становится общим получателем заявок.
4. Проверить фактическую юрисдикцию хранилищ всех почтовых ящиков и переадресации, договоры с REG.RU и почтовыми провайдерами. Не утверждать отсутствие трансграничной передачи без проверки. При необходимости выполнить требования статьи 12 до передачи.
5. Создать постоянную директорию /var/lib/athydro/applications владельца www-data с правами 0700 вне web root и релизов. Указать NUXT_CONSENT_STORAGE_DIR. Файлы заявок 0600, содержат ПД и вложения; не отдавать через nginx. В nginx для /api/send-email установить client_max_body_size 12m и ограничения частоты. API также проверяет Content-Length (требует его) и лимиты вложений.
6. Организовать контроль записей received/delivery-pending: заявка считается принятой после сохранения, даже если уведомление почтой недоступно. Ответственный должен ежедневно просматривать очередь и доставлять такие заявки; автоматический повтор писем пока не реализован. Не логировать содержимое записей.
7. Назначить ответственного за закрытие заявок и удаление. После завершения цели/отзыва без другого основания удалить запись JSON с вложениями, письма и копии не позднее 30 дней, обеспечить удаление у обработчиков и документировать уничтожение. Если другое основание требует хранения — отдельно определить состав, срок и основание. Автоматический таймер от даты подачи не заменяет определение даты достижения цели; автоудаление пока не реализовано. Определить сроки резервных копий и запрет восстановления удалённых заявок без учёта реестра удаления.
8. Установить минимальные сроки access/error logs nginx и службы; не писать тела форм, токены или пароли. Уточнить организационные меры, права доступа, резервное копирование в РФ, порядок инцидентов и действительность уведомления РКН. Наличие уведомления не проверено: без идентификации оператора это нельзя подтвердить.
9. Проверить чистый браузер, отказ/согласие/отзыв Метрики, другие вкладки, навигацию, недоступное localStorage. Проверить контролируемую тестовую заявку и вложение после настройки SMTP, затем удалить тестовые ПД. Реальные письма при локальных тестах не отправлялись.
